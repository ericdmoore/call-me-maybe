# s10 · Zero-touch handsets — the phone configures itself from handsets.toml

**Status:** planned (2026-09-21). Drafted the evening the first customer
asked "so how do I add a phone?" and the honest answer was "three fields on
each phone's web page, plus one checkbox nobody remembers until paging fails."
The server half of a handset has been generated from `handsets.toml` since
`doorman render` existed; this stream generates the other half.

## What done looks like

A factory-fresh phone comes out of the box. The MAC address on its label goes
into one `[[handsets]]` block next to a `model`. `doorman render` produces the
phone's own configuration file alongside the PJSIP it already produces;
`doorman provision` tells the operator what to press, offers the file on
the LAN for a few minutes, and shows the phone arriving. The phone is
plugged in — or told one URL, once — and boots into "Kitchen": registered with
the right password, DTMF in the mode the lobby can hear, paging auto-answer
on, codecs, clock and timezone correct, voicemail lamp wired to its mailbox,
and its admin password no longer the factory default. Nothing is typed on the
phone.

A phone whose MAC is not in the inventory is offered nothing. Nothing listens
on the LAN while nobody is provisioning. When a handset password is rotated,
every listed phone re-fetches and re-registers without anyone touching it.
`doorman check` catches a mistyped MAC, a duplicate, or a model it has no
template for, with a suggestion.

`RUNBOOK.md` → "Add a handset" becomes: one block, `render`, plug it in.

## Starting point

- `handsets.toml` knows `id`, `endpoint`, `label`, `number`, `mailbox`, `page`
  and `password_env`. It does not know what the phone *is* or how to reach it.
- `internal/render` emits per-handset endpoint/auth/AOR with the password from
  `.env`, `dtmf_mode=rfc4733` on every endpoint, `context=internal`, and the
  page-all group. That side is done and tested.
- The phone side is `RUNBOOK.md` → "Add a handset", step 3: "point the phone
  at the Pi with that username/password". Paging additionally needs "Allow
  Auto Answer by Call-Info/Alert-Info" enabled on each phone (`RUNBOOK.md:506`)
  — `[page-autoanswer]` in `extensions.conf` sends the header, and a phone
  that was never told to honour it simply rings. The invariant-9 failure
  shape, on the other side of the wire.
- Every phone ships with a default admin password on its web interface. The
  hardware table's own advice for secondhand phones — "factory-reset anything
  used; it may still be provisioned to its last owner" — describes exactly the
  mechanism this stream uses, pointed the other way.
- The site's hardware table is Grandstream-heavy (WP826/WP816, HT812,
  DP752/DP730, GRP2601P/2602P/2602W) with Yealink DECT (W70B bases, W73H/W59R
  handsets) and T31P, a Fanvil X3U and a secondhand Cisco SPA504. Grandstream
  models share one XML dialect; Yealink share another.
- Asterisk's HTTP server is bound to `127.0.0.1` and must stay there
  (invariant 2), so it cannot serve phones. There is no other listener on the
  box today, and adding one is the whole design question below.
- `.env` already holds one `HANDSET_<ID>_PASSWORD` per phone; the
  `nologsecrets` analyzer already exists to keep such values out of logs.

## Decisions and invariants

**Provisioning is rendering.** `doorman render` gains a second output
directory, `asterisk/generated/provisioning/`, holding one file per handset
in the phone's native format — `cfg<mac>.xml` for Grandstream, `<mac>.cfg`
for Yealink. These are outputs in exactly the sense of invariant 9a: never
hand-edited, never committed (the directory is already gitignored), mode
0600 because each one contains a SIP password. The templates are code-owned
`text/template` files with XML escaping, selected by `model`; this is
generated configuration, not the operator-facing "templates as data" of
`internal/tmpl`, and the distinction is stated so nobody later tries to make
phone templates user-editable.

**The inventory grows `mac` and `model`, both optional.** A handset without
them keeps today's manual path unchanged. With them, `doorman check`
normalises the MAC (colons, dashes, bare hex, any case → one canonical form),
rejects a malformed or duplicate one, and rejects an unknown `model` with a
did-you-mean. Schema, LSP diagnostics, `llms.txt` and the man page move
together, as the `internal/schema` tests require.

**The template pins the phone-side twin of every invariant.** DTMF RFC 2833
(the other half of invariant 9); `Alert-Info` auto-answer for paging; codecs
`ulaw` then `g722`; NTP and the box's timezone, because `[[schedules]]` are
local time; the message-waiting lamp bound to `mailbox`; display name from
`label`; direct-IP calling off; and an **admin password from `.env`**
(`HANDSET_<ID>_ADMIN_PASSWORD`, generated by `init` and `rotate` like every
other secret) so no phone on the LAN keeps its factory login. Where a model
has a vendor cloud agent, the template turns it off. A test asserts each of
these against every rendered file, the way `TestEveryRegistrationBindsInboundToItsEndpoint`
does for trunks.

**Serving is a CLI action, never the daemon.** `doorman provision serve`
listens over HTTPS on the LAN interface with a certificate minted once into
the state directory, for a bounded window (`--window 15m` by default;
`--forever` exists, is explicit, and warns). It answers only MACs in the
inventory — everything else is 404 — and after a phone's first fetch, the
configuration it received carries per-device provisioning credentials, so
every later fetch is authenticated. The first, unauthenticated fetch is
therefore possible only inside a window the operator opened, for a device
the operator listed. No directory listing, no plaintext HTTP, no TFTP. The
daemon never links this code: an import-boundary test asserts it, the same
guard `internal/provider` has, for the same reason — a LAN listener that
hands out SIP passwords must not share a process with the thing that answers
the phone.

**One command runs the whole session: say, serve, watch.** The operator
does not run a file server and then go looking for a log. `doorman
provision [id…]` renders if the inventory is newer than the outputs, opens
the window, and then does three things at once until every named handset
has registered or the window closes: it **prints, per phone, exactly what
to type or press** — the web path and the keypad path for that model, the
one URL, the option-66 value for a router that can hand it out, and "or
just plug it in" when the router does; it **serves**; and it **watches**,
reporting each phone's progress as it happens — the TLS connection, the
fetch, and then the registration, which it observes through ARI's endpoint
state over loopback (read-only, the same client `check` pings with). A
fetch from a MAC that is not in the inventory is refused, and the refusal
is the most useful line in the log: *"a phone at 192.168.7.51 asked for
cfg7c2e…xml — not in handsets.toml; if that is the new phone, add `mac =
"7c:2e:…"` to its block and run this again."* The operator never reads a
label with a magnifying glass. Exit is 0 when every named phone registered,
non-zero on a closed window with phones still missing, and Ctrl-C closes the
window cleanly. `render` alone prints the same instruction text, for the
operator who wants the files and not the session. The verb is provisional:
`provision` reads well with `[id…]`; `handset` as a noun (`doorman handset
serve`) is the other candidate, and the rehearsal decides.

**Rotation closes the loop.** `doorman provision notify` asks Asterisk to send
each listed phone a SIP `check-sync` NOTIFY (`pjsip send notify`, from the
CLI via `os/exec`, with a `pjsip_notify.conf` shipped alongside the other
Asterisk files); the phone re-fetches. `doorman rotate --handsets` regenerates
SIP and admin passwords in `.env` with the same validate-then-write-atomically
shape `RotatePins` has (invariant 4), then renders and notifies. A password
that lives on eight phones is only rotatable because the phones can be told.

**The URL is one the *phone* can reach, and `render` prints every form that
is true.** Never `localhost` — on the phone that is the phone. The primary
form is the box's LAN address, `https://192.168.7.133:8443/`, because every
phone on the LAN can use it unconditionally. A name is printed *as well* when
it is one the phone can use — and which names a phone can use is a **fact
per model, established by rehearsal and recorded in the model registry**,
not an assumption. The IP is the worst ergonomics and the only form that
needs no such fact. A unicast name qualifies when the box's own resolver —
the one DHCP handed it, which is the one it handed the phones — maps it to
the LAN address. An mDNS name (`jepsen.local`) qualifies for a model only
once a handset has fetched through it in this house; phones resolve through
unicast DNS by default, but some carry their own discovery paths (Grandstream's
mDNS override server, Yealink's PnP multicast SUBSCRIBE) that are worth
testing before ruling out, and a URL that works from a laptop and fails from
the handset is the worst kind of documentation, so the default is "not until
seen". A Tailscale address is never advertised by default: no
phone is on the tailnet, so it is reachable from nothing that fetches
configs; `--bind` accepts it explicitly for the remote-site or softphone
case. `serve` binds the LAN interface by default, not every interface, for
the same reason. The certificate is minted with every address it will be
offered on as a SAN, so a phone that validates can. Because the phones
register to an address as well as fetch from one, FIRST-BOOT tells the
operator to give the box a DHCP reservation or a router-provided name
before adding the first phone — a lease that moves takes every handset
down, provisioning or not.

**DHCP option 66 is supported, documented, and never required.** A router
that can hand out the provisioning URL makes the process literally zero-touch;
one that cannot means typing that URL once per phone, after which every other
setting, forever, comes from `handsets.toml`. Wi-Fi handsets have one more
unavoidable manual step — joining the network — and the plan says so rather
than pretending.

**Logs treat the MAC as a device identifier, not a caller identity.** It may
be logged in full; it is not a phone number and invariant 1 does not apply to
it. Passwords and provisioning credentials in the rendered files are secrets
under the existing analyzer, which is extended to the new template fields.

## What is deliberately out of scope

- **Vendor clouds** (Grandstream GDMS, Yealink management platforms). They
  solve this by routing the house's SIP credentials through a third party's
  servers. The whole project exists to avoid that shape.
- **TFTP and plain HTTP.** Every phone here speaks HTTPS. Credentials do not
  travel in the clear on a home LAN just because it is a home LAN.
- **Firmware management.** Phones fetch firmware from their vendor; the
  template may pin auto-upgrade off, but doorman does not host or orchestrate
  firmware.
- **Cisco SPA504.** A different dialect for a phone bought secondhand; the
  manual path stays documented for it.
- **A provisioning listener inside the daemon.** See above; not negotiable.
- **Widening Asterisk's HTTP bind to serve files.** Invariant 2.

## Milestones and acceptance criteria

### M1 · The inventory knows the phone

Add `mac` and `model` to `[[handsets]]`; a model registry naming the template
family per model (Grandstream GRP26xx, WP8xx, HT8xx, DP75x; Yealink W70B,
T3x); `HANDSET_<ID>_ADMIN_PASSWORD` in `.env.example` and `init`'s
generation. MAC normalisation with tests for every written form.

Done when `doorman check` rejects a malformed MAC, a duplicate MAC across
handsets, and an unknown model — each with a suggestion — and the schema,
LSP, `llms.txt` and man page agreement tests pass with the new keys.

### M2 · Render the phone's half

Grandstream first: one XML dialect covers the desk phones, the Wi-Fi
handhelds, the ATA and the DECT base. Yealink second. Golden-file tests per
model; a single test that walks every rendered file and asserts the pinned
settings above; files written 0600 under `asterisk/generated/provisioning/`.
`render` prints, per phone, the URL it needs and nothing else.

Done when a factory-reset GRP2601P given only that URL registers as its
`label`, answers a page on speaker, and its web login is the generated admin
password — rehearsed on jepsen with a real handset before the milestone
closes. The DP752 rehearsal covers a base carrying two handsets. The same
rehearsal settles, per model, which address forms work and records them in
the registry: the LAN IP; a router-provided unicast name where one exists;
`jepsen.local` over mDNS; DHCP option 66; and the model's own discovery
path (Grandstream mDNS override, Yealink PnP) where it has one.

### M3 · The guided session

`doorman provision [id…]`: the instruction text per model, HTTPS on the LAN
address with the once-minted certificate (`--export-cert` for phones that
validate), the window, the MAC allow-list, per-device auth after first
contact, no listing, redacted logs, the live watch through ARI endpoint
state, the unknown-MAC hint, and the exit semantics above. An
import-boundary test that nothing reachable from the daemon imports the
serving package. A sketch of the session, to be corrected by the first real
one:

```
$ doorman provision kitchen
→ rendered asterisk/generated/provisioning/cfg7c2e1a4b9c0d.xml (kitchen)
→ serving https://192.168.7.133:8443/  for 15m  (Ctrl-C to close)

  kitchen — Grandstream GRP2601P, 7c:2e:1a:4b:9c:0d
    on the phone:  Menu → System → Provisioning → Config Server Path
                   192.168.7.133:8443/prov      upgrade via: HTTPS
                   then Provision Now (or reboot)
    on the web:    https://<phone-ip> → Maintenance → Upgrade and Provisioning
    router:        DHCP option 66 = https://192.168.7.133:8443/prov
                   (then nothing on the phone at all)

  waiting for kitchen …
  14:02:11  kitchen   connected from 192.168.7.50
  14:02:11  kitchen   fetched cfg7c2e1a4b9c0d.xml  (4.1 KB, 200)
  14:02:39  kitchen   registered  PJSIP/kitchen  Avail  (rtt 3ms)
✓ 1 of 1 handsets registered — window closed
```

Done when `httptest` covers: outside the window → refused; unknown MAC →
404 plus the hint on stderr with the asking MAC; listed MAC, first fetch
inside the window → file with credentials; second fetch without them → 401;
plain HTTP → refused; and the watch, driven by a fake ARI endpoint feed,
reports connect → fetch → registered in order, exits 0 when every named
phone is registered and non-zero when the window closes first. The M2
rehearsal is repeated end to end through the session rather than a
hand-copied file, and the instruction text for each model is corrected to
what the phone's menus actually say.

### M4 · Rotation and re-provisioning

`pjsip_notify.conf` shipped with the Asterisk files; `doorman provision
notify [id…]`; `doorman rotate --handsets`. Done when rotating ends with every
listed phone re-registered on its new password with nobody touching a phone,
and a phone that was off during the rotation registers correctly the next
time it boots into a window.

### M5 · The documents

FIRST-BOOT gains a "Phones" step of three lines. `RUNBOOK.md` → "Add a
handset" shrinks to a block, `render`, and plugging in; the auto-answer
checkbox note disappears from `paging.md` because it is no longer true.
Router notes for DHCP option 66 (the option value is the URL). The hardware
table gains a column saying which models are templated.

Done when no document tells anyone to type a password into a phone.

## Alternatives rejected

- **Answer any phone that asks.** A provisioning server that hands a
  configuration to an unlisted MAC is the "still provisioned to its last
  owner" hazard, built on purpose. Only listed devices, only in a window.
- **Always-on serving by default.** A permanent LAN listener holding every
  SIP password, to save opening a window a few times a year. No; `--forever`
  is there for the operator who has decided otherwise, and it says so.
- **One universal template.** Vendors do not share a dialect; pretending they
  do produces a template nobody can read. One per family, small, golden-tested.
- **Serving from Asterisk's HTTP server.** Loopback-bound by invariant 2, and
  widening it exposes ARI. The two must never share a bind.
- **Letting phones keep their factory admin password.** It would simplify the
  template by one line and leave the weakest device on the network exactly as
  weak as it arrived.
- **Requiring DHCP option 66.** Consumer routers often cannot; a plan that
  needs a router upgrade is not zero-touch for the people this is for.

## Rollout order

M1, then M2 for Grandstream with the jepsen rehearsal on a real handset, then
M3 — the two rehearsals are the acceptance test, and neither happens without
a phone on the desk. M4 follows once serving is trusted. Yealink templates
land under M2's tests whenever a Yealink is available to rehearse against.
M5 tracks whichever models are actually verified; it never claims a model
that has not registered in this house.

s09 M1 (embedded assets) lets the templates ship inside the binary; until
then they live in the checkout like the Asterisk files do. Nothing here waits
on it.
