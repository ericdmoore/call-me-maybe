# s05 · System alerts — development plan

How doorman tells the household something it needs to know, using the only
output device the household has agreed to pay attention to: the telephone.

**Status:** planned. Nothing started.
Related: `.plans/s03-provider-balalnce-checking` (first real customer),
`docs/TASKS.md` §2 (voicemail, transcription), issue #15 (outbound alert
ladders), `.plans/README.md` (composite prompts primitive).

---

## Why

Several things doorman will eventually know are worth telling somebody, and
none of them currently have anywhere to go:

- A trunk balance that will run out in about a fortnight.
- A new doorman release.
- A TLS certificate that renews on Monday and did not.
- A watchdog that has restarted the same service four times today.
- A prompt pack referencing a clip that is not installed.

Email is the obvious answer and it is the wrong one for a household. Nobody
reads the Pi's email. The phone, on the other hand, is the device this project
already owns, already speaks through, and that everybody in the house responds
to.

---

## Two deliveries, one catalogue

Every alert is a message. What differs is urgency, and urgency picks the
delivery.

### `live-call`

doorman originates to a handset or paging group, speaks the message, and
optionally waits for a DTMF acknowledgement.

**Costs nothing and works when everything else is broken.** An internal call
never touches a trunk — no provider, no credit, no registration required. A
trunk that is dead, unregistered, or out of money can still ring the kitchen to
say so. This is the property that makes the whole feature possible and it is
worth stating plainly, because the obvious objection to alerting about a dead
trunk is "how would it tell you".

### `straight-to-vm`

doorman renders the message and **writes it into a mailbox without placing a
call**: the audio into the voicemail spool, with its metadata file alongside.

From there every existing mechanism does its job unchanged:

- `app_voicemail` lights the MWI lamp on the handsets.
- The message is emailed with the WAV attached (`attach=yes`, already
  configured).
- The `externnotify` hook (TASKS §2) transcribes it and emails the text.
- It plays back through `*97` like any other message.

So a system alert becomes an ordinary voicemail, with audio *and* a transcript,
and almost nothing new is built to get there.

### Which one

Severity picks the default; the operator may override per message type.

| Message | Default | Why |
|---|---|---|
| Water sensor, alarm | `live-call` + ack | act now, and prove somebody heard |
| Balance critically low | `live-call` | the trunk dies within days |
| Balance trending down | `straight-to-vm` | read it this week |
| New doorman version | `straight-to-vm` | never urgent |
| Certificate renewal failed | `straight-to-vm` | urgent tomorrow, not tonight |

## No runtime speech synthesis

**Invariant 7 holds here too.** Messages are assembled from pre-rendered
phrases and `digits:`, not generated by a TTS call at alert time:

```
"Your VoIP dot M S balance is"  digits:12  "dollars"  digits:34  "cents"
```

That is the **composite prompt** primitive — third customer, after reading a
line's own number back and "call from area code XXX". Build it once.

The consequence, and it is the right trade: **alerts are templates with slots,
not arbitrary text.** A fixed catalogue of system messages is exactly the case
where that is fine, and refusing arbitrary text is what keeps a TTS dependency
off a path that runs unattended at three in the morning.

Every phrase ships pre-rendered in the bundled pack, so an alert works on a
fresh install with no account, no key and no network — the same standard the
six lobby prompts are held to.

## Milestones

### M1 · The catalogue and `straight-to-vm`

Voicemail delivery first: it needs no handset to be free, cannot wake anyone,
and is the safe default to get wrong.

- An `alert` package: message types, severity, template slots.
- Render via composite prompts.
- Write to the voicemail spool with correct metadata.
- One real customer end to end — s03's "balance trending down".

**Verify:** the MWI lamp lights, the email arrives with audio attached, and
`*97` plays it back. If the transcription hook exists, the transcript arrives
too.

### M2 · `live-call`

- Originate to a configured handset or paging group.
- Optional DTMF acknowledgement, with the outcome recorded.
- Repeat-suppression, so a low balance does not ring the kitchen hourly.
- Quiet hours respected — an alert that is not urgent must not wake the house,
  and `[[schedules]]` already exists to say when that is.

### M3 · Escalation

The general principle this feature contributes to issue #15's ladder:

> **Escalate from free and local to paid and remote.** Rung one is a handset —
> free, works when broke. Rung two is a mobile over the PSTN, which costs money
> and needs the very balance the alert may be about.

- A ladder per severity, reusing `policy.RingPlan` rather than inventing one.
- Acknowledgement stops the ladder.

### M4 · More sources

Release checks, certificate expiry, watchdog restarts, missing pack clips.
Each is a small producer against a catalogue that already exists.

## Rules

- **Never on the inbound call path.** Alerts are timers and background checks.
  A caller must never wait on one.
- **Never on a trunk when a handset will do.** Local first, always.
- **Never wake the house for something that can wait**, and honour quiet hours
  for anything below critical.
- **Never repeat without suppression.** An alert that rings hourly is an alert
  that gets ignored, which is worse than not sending it.
- **Never speak a secret.** The `nologsecrets` discipline applies to spoken
  output as much as to logs — a balance is fine, an API key is not, and a
  message read aloud in a kitchen is a message a guest can hear.

---

## Risks

| Risk | Mitigation |
|---|---|
| Alert fatigue makes every alert invisible | Few message types, suppression, severity that means something |
| An alert rings at 3am about a software update | Quiet hours honoured below critical; `straight-to-vm` is the default |
| Voicemail spool format changes under us | One small writer, covered by a test against a real mailbox layout |
| The alert path breaks call handling | Separate goroutine, non-blocking, and it may never touch a session |
| Somebody adds arbitrary-text alerts and reaches for runtime TTS | The catalogue is a fixed set of templates. Stated here so the pressure is recognised when it comes |

---

## Out of scope

Arbitrary user-authored alerts · SMS delivery · a notification-rules engine ·
anything that phones a number the operator did not configure.
